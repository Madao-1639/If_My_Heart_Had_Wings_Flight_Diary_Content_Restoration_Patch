## Arc 归档容器格式 ✅

### 头部（8 字节）

```
offset 0: count       (uint32, LE)  — 成员数量
offset 4: table_size  (uint32, LE)  — 条目表总字节数
```

无文本 magic 签名。`data_start = 8 + table_size`。

### 条目表（紧随头部，重复 count 次）

```
size            (uint32, LE)  — 成员数据字节数
relative_offset (uint32, LE)  — 相对 data_start 的偏移（不是文件绝对偏移）
filename        (UTF-16LE，以 \x00\x00 结尾)
```

## WS2 剧本脚本格式 ✅

### 尾部 8 字节 = **明文尾表** ✅（`[u32 消息数][u32 选项条目数]`）

成员最后 8 字节是**明文**（**不参与** rotate-6 混淆）：

```
+size-8  u32  消息数（= 0x14 台词条数）
+size-4  u32  选项条目数（= 0x0f 各块条目数之和）
```

- 引擎**加载脚本时**读它（`data[size-8]` / `data[size-4]`），据此给「已读消息位图」（存档目录 `MessageFlag.dat`，记录 = `脚本名 UTF-16LE\0` + `u32 A=8+位图字节` + `u32 B`(已标记次数) + `u32 Y` + 位图）分配 `(消息数 + 选项条目数 + 7) / 8` 字节。
- 写位函数 `bitmap[idx>>3] |= 1 << (idx&7)` **不做边界检查** ⇒ 尾表小于脚本真实消息数时，高位下标直接写到相邻堆块上，延迟到某次 `free` 被堆校验抓到 ⇒ `0xc0000374` **概率性闪退**（不会崩在写位处；也可能先在 Lua/UI 上表现为随机 nil 错误）。
- **实机指纹**：`MessageFlag.dat` 内该脚本记录的位图容量明显小于脚本消息数（如 `HOT_004_E` 96 B↔762 条，而脚本已 1319 条），且该记录的 `B` 持续增大而位图仍为 0（写位全部落在容量外）；重命名 `MessageFlag.dat` 可暂时不闪退（堆布局变化掩盖），但容量仍按旧尾表分配。
- ⇒ **任何改变 `0x14` / `0x0f` 条数的改写（插入、删格、拆格、换脚本、跨版本搬运）都必须同步重写这 8 字节**，且要写成**明文**、在 `encode()` **之后**写（先写会被旋转成垃圾）。
  - 落地点：`tool/writer.py::rebuild_host`（host 重建）、`script/build/build_patch.py`（whole 路径）；
  - 工具：`tool/ws2.read_tail_counts / tail_counts / set_tail_counts / check_tails`；
  - 闸：`script/checks/ws2_tail_check.py`（产物逐成员 `尾表 == 实算`）、`script/final_verification.py` 的 9b 项。
- ⚠️ **解析约定**：解码流里这 8 字节是「明文的 rotate-6」（读出来是 `0x8060` 之类的垃圾）。本作反汇编把 `0xff` 当 **9 字节**（`ff` + 这 8 字节）消费，因此 `tool/ws2dis.TAIL_LEN = 0` 只表示「9 字节 FileEnd 之后**不再有**追加字节」，**不代表成员没有尾表**。
- ℹ️ **`MessageFlag.dat` 的记录容量不会随脚本增长而重算**（记录按首次写入时的尾表定长），所以装了补丁后旧记录可能偏小。**但存档/已读表属引擎存档系统，不在本项目工作范围**：安装器不读不写它，本项目也不对其做转换。上面这些只是**诊断口径**（判断尾表是否过期），不是交付动作。

### `0x0f` 选项表（ShowChoice）：条目**内联**、且**各占一个 `.lng` 槽位** ✅

```
0f <count:u8>
count × ( <strid:u16> <text:cp932>\x00 <u16 标签> <u8 0> <jump> )
jump = 06 <u32 文件内绝对偏移> | 07 <脚本名>\x00
```

- **条目内联在 `0x0f` 的操作数里**（引擎在 `0x0f` 处理器内按此布局读，格式表的 `0x0f = [0]` 只声明 count）。⚠️ 条目首字节常恰好是 `0x5e`/`0x5f` 这类合法 opcode，**按普通指令切分会把条目劈成伪指令**；一旦重编 `strid`（改变条目首字节）整条流立刻失步。正解：`tool/ws2dis.choice_entries / choice_block_end` 把整块当一条指令。
- **文本槽位等式**：`0x14` 的 `id` 与 `0x0f` 各条目的 `strid` **共用一个按文件顺序递增的计数器**，选项文本**也占 `.lng` 槽位** ⇒ **`lng 条数 == 0x14 条数 + Σ(0f count)`**（占位行 `%N`/`%P` 同样占位）。原版的指纹：`BEF_004` 的 `0x14` id 在 `605 → 608` 之间**空出 606/607**，正是那张二选一的两个条目。
- 归零口径：产物写盘后用 `tool/ws2.repool_text_ids()` 按文件顺序统一重排（`0x14` id + `0x0f` strid）；`.lng` 由 `resource/slot_sources.json` 逐槽构建（选项槽来源 `['choice', 原版 strid]`，中文取 `resource/corpus/choice_cn.json`）。
- 中文来源：原版无 `.lng`（日文即条目内联 `<text>`）⇒ **ws2 保留原文，`.lng` 写对应中文**；缺译即构建失败（不允许回落日文）。

- **选项头 `0x0e`（必须由产物自己发）** ✅ —— 每个 `0f` 之前要有一条 6 字节头 `0e 0b 00 <count:u8> 00 01`，`count` 必须等于该 `0f` 的 count。
  证据（`[语料]`）：同代且**选项实机可用**的本篇（IMHHW）Steam 版里 `CO1_020` = `0e 0b 00 04 00 01` + `0f 04`、`HUT_005` = `0e 0b 00 02 00 01` + `0f 02`；另有 4 个脚本是**无 `0f` 文本表**的条件式变体（头后跟 `01` 条件组 + `0b <u16 flag> 00`）。
  本作局面：Steam 侧 **119 个 ws2 里 `0e 0b 00` 出现 0 次**（`0x0e` 只在 `mainmenu.ws2` 以**时序块形态** `0e 00 00 e8 03 00` 出现 8 次），原版（更早一代）也不用这条头 ⇒ 只能由产物补；缺头时的实机表现未验证，按同代语料一致做法必须发（闸 9c 守）。
  实现：`tool/writer.choice_hdr()`；`rebuild_host` 在发出 `0f` 前**自动补头**（幂等，原版侧自带头时不重复发），并把头的 6 字节计入 `rel` 以保证块内跳转（含条目自带的 `06`）正确重定基。
  闸门：`script/checks/choice_header_check.py` 与 `script/final_verification.py` 的 **9c**（每张 `0f` 前必须是 `0e`，形态与 count 都要对）。

### 选项编写规范（本作；还原与**新增**共用）✅ 结构 / ✅ 交互

> 适用：还原原版选项表、以及今后**新增**选项。每条都标了证据类型；❓ 项在没有证据前**不许猜**。

**A. 结构（已定案）**

1. 一张选项 = `0e 0b 00 <count:u8> 00 01`（选项头）+ `0f <count>` + `count` 个内联条目。
   - 条目：`<strid:u16><text:cp932>\x00<sep:u8><label:u16><jump>`
     - `sep`：本作原版 = `0x80`；本篇 = `0x00`（沿用所属语料，别混用）
     - `label`：**写盘一律写 `0x0180` + `0x00`**（字节 `80 01 00`；亦可读作「`0x80` 标记 + `u16 = 1`」，指同一段字节）。本篇同代语料按条目递增（`0x0b00/0x0c00…`），该差异不影响显示与选中。
     - `jump`：`06 <u32 文件内绝对偏移>` 或 `07 <脚本名>\x00`
   - `[语料]` 选项头的必要性：本篇（同代、选项实机可用）6/6 个含选项脚本都有；本作 Steam 0/119、原版 0/108（原版更早一代）。故**产物必须自己发**。
2. **文本顺序 = 文件顺序**，`0x14` 的 id 与条目 `strid` 共用同一个递增计数器 ⇒ `lng 条数 == 0x14 条数 + Σ(0f count)`。
3. 提示句：`0f` 之前必须有一条 `0x14`，尾标记用 **`%K`**（只留框不清框）。`[语料]` 原版 `BEF_004`：`605` 尾 `%K`，其前三条都是 `%K%P`。
   - ⚠️ **选项帧内不得有 `0x16`**：本作 Steam 侧的 `0x16` 会把 `MenuInf.enabled/effect` 推成 `false/true`（`closeMessageWindow`/`15/50` 的效果），输入门 `GetMenuMouseEnable` 因此恒不通过 ⇒ 选项能画、无悬停、点不动、`selCursor` 不变。删掉它之后：悬停/点击/两条分支正常，**提示句留在框内与选项同屏**（正是原版的"留框提示"语义，C+C 的惯例在本作同样成立）。原版（老一代 Lua，无 `enabled/effect` 状态机）容忍这条指令 ⇒ 属代际差异，还原时按目标引擎剔除（写盘期实现：`tool/ws2.drop_choice_frame_op16()`；闸门 9g）。
4. 每条分支的落点首格应有纯标记 `14 "%P"`（清框），本作与原版一致；落点不得落在条目/字符串中间。
5. 分支出口：前一条分支末尾 `06 → <汇合点>`，最后一条分支**落到**汇合点（不写 `06`）。汇合点通常是一段演出块（`16 00` / `64 00` / `33 …`）。
6. 选项期**不得有语音**（`0x28` 播放、`0x15 <非空名>`）；`[语料]` 原版 `BEF_004` 的选项帧内 `0x28` 计数 = 0、`%LC` 计数 = 0。
7. 人名帧：`0x15 <名>` 是**流状态**，作用到其后第一条 `0x14`；选项条目继承该状态。产物把原版的 `%LC<日文名>` 映射为 `%LC<罗马字键>`（`NameTable.txt`），这是**唯一允许**的人名差异。

| 项 | C+C 做法 | 本作是否适用 | 依据 |
|---|---|---|---|
| 选项头 | 每个 `0f` 前 `0e 0b 00 <count> 00 01` | **适用**（本作 Steam 侧无选项，需自补；闸 9c 守） | 本篇同代 6/6 都有；本作 0/119 |

### 变体路由（choice / route）的字节形态与纪律 ✅ 已定案（2026-10-27 实机校正）

「同一段剧情保留两套演绎、分支点让玩家选」在本作有两种接法，都属**选项编写规范 A1** 的延伸：

| 接法 | 适用 | 形态 | 本项目实现 |
|---|---|---|---|
| **choice（帧内跳转）** | 分支两侧都在同一脚本 | 选项帧（`15 00 00` + `14 %K` + `0e 0b 00 n 00 01` + `0f`）→ 各分支前奏 `0b var <旗标>` + `14 "%P"` → 分支体 → 非末支 `06 → 汇合点` | `tool/variants.apply_choice`；分支 B = Steam 行区间原字节 |
| **route（跨脚本变量路由）** | 一组后续脚本整体切换版本 | 目标脚本首条 `01 mode=2 var == 0 → <Steam 体起点>`；原版体在前、Steam 体整段追加在后，各以 `07 NextFile` 收束 | `tool/variants.apply_route`；Steam 体 = 整脚本体原字节 |

**变量纪律（实机校正的硬约束）**

1. **布尔旗标只能写 0/1**，路由条件必须是 **`01 mode=2 (==) var == 0`**（成立⇒顺序执行＝原版体；`var=1`⇒跳 Steam 体）。
   `0b` 是**布尔**存储：写 `2` 与写 `1` 在布尔比较里都等于 true ⇒ `01 var != 2` 对两个选项都判假、**两条分支走同一体**（本作 2026-10-27 实机事故：两个选项都进 Steam 体；字节形状检查全部通过）。
2. `== 0` 还带来**缺省安全**：未写入也等于 0 ⇒ 走原版体（回想/半途进入不会被莫名换成 Steam 版）。
3. **原版分支不挂 Steam 的解锁/成就**：变体脚本删除 Steam 行时，该行的 **CG 固有组（`0b` 解锁对 + `04 CG_ACHIEVEMENT`）不再保留**（`tool/writer.drop_units(no_ach_slots=…)`，由 `build_patch` 按变体表划定范围：choice=接缝→汇合点，route=整脚本）；其余 `0b`（场景旗标）/`04`（非成就调用）照旧保留。成就与鉴赏由 Steam 分支原生提供，实机口径见 [restoration-scope.md](restoration-scope.md) §8。
4. 需要三态以上时，别硬塞布尔：改 `09`（浮点变量）+ `01` 的 bit7 浮点比较——**本作全库无 `01` bit7 先例**（`09` 仅 9 个 id），启用前必须实机验证。引擎级说明见 GalRev `docs/engines/advhd/branching-and-variants.md`。

**偏移纪律**

- 分区线性重定基：`map(t) = t + Σ{此前插入区的净增量}`（按源区间累加，不要逐条累加）；
- 追加体内部偏移统一加「追加体起点 − 源起点」一个 delta；
- `0f` 条目的跳转是**块内绝对偏移**：对单条指令做重定基时**不要**再叠加 `off+1`（本作踩过 off-by-one，症状是"pack_into 越界 / 落点落在指令中间"）；
- 插删后必须重算**末尾 8 字节明文尾表**（见本文「尾部 8 字节」）。

**闸门对应（形状面全自动）**：`variant_route_check` 按 `slot_sources[sc].variant.targets`（brA/brB/conf）回读——条目落点、`0b` 旗标值、`14 "%P"` 前奏、`0e` 头、提示句、汇合点、Steam 体逐指令等值、分支体画廊解锁点归属。

**但形状检查不覆盖「两个选项是否真的通向不同内容」**——布尔折叠那类错误字节完全合法。**每条 route/choice 必须实机各点一次、比对一句标志性台词 + 一张标志性图**（`doc/acceptance-criteria.md` 实机项）。

### 已确认的操作码/操作数模式

从实际解码内容中观察到的模式（十六进制，`XX` 代表可变字节）：

- **对话行**：`\x14 <idx:u16> <flag:u16> char\x00 <Shift-JIS文本> %K%P|%P|%K`
  - 格式详解：
    - `\x14`：对话行标记
    - `idx`：2字节小端序无符号整数，lng文件索引
    - `flag`：2字节小端序无符号整数，标志位（用途待确认）
    - `char\x00`：固定标记，表示后续为对话文本
    - 文本内容：Shift-JIS (cp932) 编码
    - 结束标记：`%K%P`（最常见）、单独`%P`、单独`%K`
      - `%K`：换行/等待用户点击
      - `%P`：清空文本框
  - 文本可能包含角色名前缀：`%LC<角色名>\x00`（如 `%LC小鳥\x00`）
  - CRC32计算方法（用于匹配翻译表）：
    1. 提取完整文本（包含 %LC/%K/%P 等标记）
    2. 使用 cp932 解码为 Unicode 字符串
    3. 转换为 UTF-16LE 编码的字节序列
    4. 计算 CRC32，作为有符号 int32（若 ≥ 0x80000000 则减去 0x100000000）
  - 提取正则表达式：`\x14(.{2})(.{2})char\x00((?:[\x80-\xff\x00-\x7f])*?(?:%K%P|%K(?!%P)|(?<!%K)%P))`
- **背景/立绘显示**：`\x33 <槏位名，如 st01/bg01> \x00 <资源名.PNG> \x00 ...` 后紧跟 `LAYER_ORDER` 表
- **跳转/调用到其他脚本**：操作数格式为 `\x02 <脚本名，ASCII 大写，无扩展名> \x00 <4字节数值>`（已在 `ASA_001.ws2` 末尾实测确认，指向 `ASA_002`/`ASA_003` 等）——提取引用时必须用精确字节匹配（脚本名前后有非文本控制字节），不能用朴素子串匹配
- **选择分支菜单**：`\x0f <选项数> [ <id:u16> <选项标签>\x00 <3字节> \x07 <目标脚本名>\x00 ] ...`。标签是**裸 Shift-JIS 文本、无 `%K`/`%P` 标记**；`FLAG_CHECK` 变量表同构（`\x04 FLAG_CHECK \x00 \x0f <项数> [ <id:u16> <标签>\x00 <8字节> ] ...`）。已实测确认（`CO1_013`/`CO1_016_A`/`CO1_018`/`CO2_005`/`HUT_005`），提取见 `tool/scriptext.py` 的 `script_rows()`（`kind='menu'`/`'flag'`）
- **`LAYER_ORDER` 调用与白名单表**：脚本里的 `\x04 LAYER_ORDER\x00` 是 **RunFile 子程序调用**（调用归档内 `LAYER_ORDER.ws2`），不是数据表。`LAYER_ORDER.ws2` 本身是**纯键名白名单**，两版**逐字节相同**（已实测）：
  ```
  0x3f <count:u8=0x13> ev\x00 bg01\x00 bg02\x00 st01\x00…st12\x00 movie\x00 text01\x00 text02\x00 text03\x00 0x05 0xff…
  ```
  → 19 个键（`ev`；`bg01-02`；`st01-12`；`movie`；`text01-03`），**不含位置/坐标**。
- **立绘/背景块指令**（易混）：`\x04 LAYER_ORDER\x00` 之后是若干 `\x09 <index:u16> <float>`（图层权重）与 `\x46 <槽位名>\x00 …`（图层定位）——这是**块的指令流**，不是 `LAYER_ORDER` 表内容。两版该类指令存在增删差异，属演出指令层差异，见 [engine-mechanics.md](engine-mechanics.md)。
- **`0x46` 图层定位的两形态与跨引擎标志差 ✅**：每个显示块的 `0x46` 有两种形态——① **子层槽绑定**（操作数 = 通道`\x00` + u8 + u8 + **u16 标志** + 4×f32 层槽 id，id 实测恒为 10–13）：把该通道 PNA 的子层绑到引擎层槽；② **坐标定位**（标志 u16 恒 `0x0000` + 坐标浮点）。**标志 u16 的取值按引擎版本编码**：**原版工具链写 `0x0080`、Steam 工具链写 `0x00f0`**（两侧全库 ~7.6k 处零交叉；`0x0000` 两版一致）。`0x80` 不在 Steam 引擎自身词表内 ⇒ **移植原版指令必须归一 `0x80 → 0xf0`**（`tool/ws2conv.norm_flags()` 整表走一趟，`build_patch.prep_orig` / `writer.rebuild_host` / 各闸共用；闸 `script/checks/op46_flag_check.py`），与 `0x39` 记录号映射同类的跨引擎移植归一。⚠️ `0x80` 的引擎行为与实机「立绘遮挡 CG」的根因无涉（归一后遮挡依旧，2026-10-26 实测）——真根因与修复见 [lessons-learned.md](lessons-learned.md) 「立绘遮挡 CG」真根因…条。
- **`0x47 Effect1` 的参数来源标志 `B` 属同一类词表差 ✅**：布局 `<通道>\0 <特效>\0 <u16 sel> <u8 A> <u8 B> <f32 p0..p4> <u16 X> <f32 秒>`；`B` 的 bit7 ＝「后随 5 个 f32 是浮点变量表索引」（原版 handler `sub_44E060` 实读）。原版工具链 `B ∈ {0x00, 0x80}`、Steam 工具链 `B ∈ {0x00, 0x10, 0xc0}`（零交叉）⇒ **移植时必须归一**：`0x80 → 0x10`（上一条 `0x45` 的 type = 6，字面模式）／`0x80 → 0xc0`（其余，变量模式）。实现在 `tool/ws2conv.norm_flags()`（`0x46`+`0x47` 同走一趟，按脚本顺序），闸同 `op46_flag_check.py`；字段语义与依据见 [engine-mechanics.md](engine-mechanics.md)「`0x47 Effect1` 语义与跨引擎标志换算」。
- **`0x01` 条件跳转**：**`01 <mode:u8> <id:u16> <val:f32> <a:u32> <b:u32>`**（共 16 字节）。语义统一为「**`var[id] OP val` 成立则顺序执行，否则跳到 `b`**」，`OP` 由 `mode & 0x3F` 决定；`b` 是**解码流内的绝对字节偏移**（真实 Steam 库 2116/2116 个可解析目标全部对齐到指令起点）⇒ 对指令流做任何插入式修改后，`b` 必须按目标指令的新偏移重定基（`script/build/convert_sl_ws2.py` 已实现）：

  ⚠️ **`a` 并非恒 0**：`a` 是第二个候选目标，**`a != 0` 时优先于 `b`**（例：`mainmenu.ws2 @0x38` `var[99] == 100 -> 0x15a (a=0xb8)` 的 if-else-if 派发链）⇒ `a`/`b` 两个字段都要各自重定基，值为 `0` 表示「无此目标」必须跳过。

  ⚠️ **携带绝对偏移的不止 `0x01`**：`0x02` / `0x06`（均 `02|06 <target:u32>`，格式 `04 ff`）是**无条件跳转**，整个操作数即绝对偏移 ⇒ 插入式转换同样必须重定基。`REBASE_OPS = {0x01: (7, 11), 0x02: (0,), 0x06: (0,)}`（值 = 目标 u32 在操作数内的偏移）。

  | `mode & 0x3F` | OP | `mode` 其他位 |
  |---|---|---|
  | 0 | `>=` | bit6(`0x40`)：右操作数也是变量（`val` 作变量下标） |
  | 1 | `<=` | bit7(`0x80`)：走**浮点变量**路径（否则走布尔变量位图路径） |
  | 2 | **`==`** | |
  | 3 | **`!=`** | |
  | 4 | `>` | |
  | 5 | `<` | |

  `2`/`3` 的取向由 `sub_459DA0` 的反汇编（jumptable case 2/3 的 `ucomiss` + `lahf`/`test ah,44h`/`jnp` 走向）判明，并用 `CG_Achievement.ws2`、`mainmenu.ws2`（`var99 == 105`、`var127 == 0`）三处独立用法交叉验证。
- **`0xF0` 成就触发**：`f0 <idx:u8>`（共 2 字节）。`idx` = Steam 成就枚举序的 0 基序号；越界（本作成就数 = 20）则为空操作。引擎分发表表项 240 → `sub_46AC00` = `ISteamUserStats::SetAchievement` + `StoreStats`。触发契约见 [engine-mechanics.md](engine-mechanics.md) §成就触发点契约；完整映射见 [achievement-mechanics.md](achievement-mechanics.md)。
- **`0x09` 变量设置**：`09 <mode:u8> <id:u16> <val:f32>`（共 8 字节）。`mode=0` 赋值、`mode=1` 累加（`var[id] += val`）。
- **`0x0b` 布尔变量设置**：`0b <id:u16> <val:u8>`（共 4 字节）。
- **格内指令的归属次序 ✅**：一个文本单元的典型排布是 **演出指令（`0x33`/`0x34`/`0x1e` 及其 `LAYER_ORDER` 块）→ `0x28` 语音 → `0x15` 名字框 → `0x14` 文本**。⇒ 语音与画面 token 归**其后最近的一条 `0x14`**；该行自身不带时**沿用前一格**的生效值（语音与画面都是延续语义）。承载图取数、`script/checks/perf_sync_check.py` 的逐槽对账、`tool/scriptext.script_rows()` 的 dlg/ctrl 序都用这一口径。本作实测自证：8,831/8,993 条语音的 OGG 角色码与其后 `0x15` 名字一致，仅 8 条只与前一个名字一致 ⇒ 前缀归属成立。
  - 连带后果：删格（`tool/writer.drop_units()`）只摘被删行的 `0x14` 与其邻接 `0x15` ⇒ 该行**前面的演出与语音指令整段留在原地**，按上述口径落进**后继格**的归属区（表现为"无对白连播语音""画面/立绘/BGM 回退"）。分诊与处置见 [restoration-route.md](restoration-route.md) §7 V-9、[lessons-learned.md](lessons-learned.md) 「「某类残留无害」的结论必须写下它依赖的前提」条。

### 两版操作数格式表与原版脚本转换

引擎在二进制内自带一张 **256 项操作数格式表**（指针数组，每项指向 `0xff` 终止的操作数类型码串；类型码 `0/1`=u8(u16)、`2`=u16、`5`=f32、`6/9/10`=str、`8`=0B、`7`=变长块）。这是 WS2 线性解析的**权威依据**：

- **Steam 表**：脱壳 exe `off_553EC0`，即 `tool/ws2fmt.txt`（158 项非空）。
- **原版表**：原版 `AdvHD.exe`（未加壳）`.data` 内文件偏移 **`0x1212c0`**（98 项非空；自校验：entry[0x21] 必须指向 `06 08 01 01 01 ff`）。

两表逐项差分：

1. **Steam = 原版 + 尾部操作数 + 新增操作码**，不存在「原版有、Steam 无」的操作码（第三类差分为空）⇒ 原版脚本转换到 Steam 编码总是可行。
2. 格式不同的操作码共 9 个，新增操作数的取值**恒定**（依据见下表后的「插入取值的独立验证」）。⚠️ **`CO1_001`/`CO1_002`/`CO1_003`/`CO1_015`/`HUT_004` 等同名配对脚本不能用于验证取值**：这几组成员的指令序列在 Steam 侧本就不同（`CO1_001` 原版首条 `0x16` vs Steam `0xf0`；`CO1_003`/`CO1_015`/`HUT_004` 在指令 4–5 处 Steam 已删/改演出指令），naive 序号对齐会把不同指令的操作数配在一起。同名配对只用于确认「操作码存在性与格式表差分」。

| op | 原版 fmt | Steam fmt | 转换（实测取值） |
|---|---|---|---|
| `0x11` | `06 08 05` | `06 08 00 05` | str 与 f32 间插 `0x00` |
| `0x14` | `04 06 08 06 08` | `… 00` | 尾插 `0x00`（全库 43886 条验证） |
| `0x15` | `06 08` | `… 00` | 尾插 `0x00`（87739 条） |

### 成就注入机制 ✅ 已完全确认（脚本层 + 引擎层）

Steam 版 `Rio.arc` 中存在一个原版没有的独立脚本 `CG_Achievement.ws2`（9606 字节），是一段**以 CG 编号为键、维护 CG 收集计数并触发收集类成就的 VM 字节码**。触发契约见 [engine-mechanics.md](engine-mechanics.md) §成就触发点契约；完整映射链（29 处 `0xF0` 触发点 → 20 项成就）见 [achievement-mechanics.md](achievement-mechanics.md)。

**结构 ✅ 已逐字节复核**（解码后 9606 字节 = 8 字节头 + 395 × 24 字节记录 + 118 字节尾部）：

```
头        : 09 00 37 00 00 00 00 00                  ; LayerConfig(mode=0, id=55, 0.0) —— 初始化 CG 计数器
每条记录  : 01 02 <u16 CG编号> 00 00 80 3f           ; Condition(mode=2, id=CG编号, val=1.0, b=下一记录)
            00 00 00 00 <u32 下一记录偏移>           ; a = 0；b 恒为 (本记录偏移 + 24)，正向链表
            09 01 37 00 00 00 80 3f                  ; LayerConfig(mode=1, id=55, 1.0) —— var[55] += 1.0
尾部      : 6 × [ Condition(mode=0x80, id=55, <float 阈值>, b=下一块) + F0 <u8 idx> ] + 05 + ff + 8 字节尾
```

- **本文件是 VM 字节码，不是不透明数据表**。每条记录语义：`if (var[CG编号] == 1.0) var[55] += 1.0`（`0x01` 的 `mode&0x3F == 2` 即 `==`：成立则顺序执行，否则跳 `b`）。`var[CG编号]` 由显示点处的 `0x0b <CG编号> 01` 置 1。
- 395 条记录的 CG 编号 = **1190 … 2674**，严格递增、互不重复；表内**无任何 ASCII 字符串**（成就名不在脚本层）。
- 尾部 6 条 `F0 <u8>` 是**成就触发指令**（`F0` = `SetAchievement`，完整映射见 [achievement-mechanics.md](achievement-mechanics.md)），阈值依次为 **1 / 79 / 158 / 237 / 316 / 395**（即 1 个 CG 与 **20% / 40% / 60% / 80% / 100% × 395**），索引 `14/15/16/17/18/19` ⇒ 成就 `IMH_ACHIEVEMENT_15..20`（First Contact / Approach / Take-Off / Soar / Glide / Morning Glory）。
- 常量尾巴 `09 01 37 00 00 00 80 3f` 在 `Rio.arc` 全部 **158 个 `.ws2`** 中**只出现在本文件**（395 次），是成就表专用模板；记录里的 `01 02 <u16> 00 00 80 3f` 则是通用写法（其他脚本共 1420 次，见 `CG_PAGE01-12`、`FLAG_CHECK` 等）。

**键值对应 ✅ 已核对**：`CG_Achievement.ws2` 的 395 个编号集合 **= 全部 CG 显示点的第二个 `0x0b` 变量（B）取值集合（394 个）∪ {1195}**，一一对应、无一遗漏；表内多出的 `1195` 在 Steam 脚本中没有任何显示点（疑似被删 CG 的遗留条目）。

对比同一场景脚本（如 `AGE_001.ws2`）在 Steam 版与原版的对应位置，发现显示 CG 的指令序列中，Steam 版比原版多出一段：

```
原版：  ...LAYER_ORDER\x00 <resource-id>04 01 0b <id2> \x01\x04 LAYER_ORDER\x00...
Steam版：...LAYER_ORDER\x00 <resource-id>04 01 0b <id2> \x01\x04 CG_ACHIEVEMENT\x00 \x04 LAYER_ORDER\x00...
```

即：显示 CG 的固有指令（含两个内在 id 字段，原版就存在，与成就无关）之后，Steam 版额外插入了一条 `\x04 CG_ACHIEVEMENT \x00` 调用指令。已确认 51 个脚本文件包含对 `CG_ACHIEVEMENT` 的调用；用正则匹配全部 0x33 CG 显示指令逐一核对，Steam 版 `Rio.arc` 全部 **158 个 `.ws2`** 中共有 920 处 CG 显示，全部 920 处紧跟成就调用，覆盖率 100%——即 Steam 版对每一次 CG 显示都无条件注入了这条调用，不是选择性注入。

**注入方法（已实现并验证，见 `tool/ws2.py` 的 `inject()`）**：向脚本中插入内容时，若该场景在 Steam 版中存在对应的 CG 显示点，直接复用 Steam 版脚本中已经写好的这条调用指令，绝不重新计算或编造内在的 id 字段。已验证：从一段真实 Steam 脚本中剥离全部成就调用后，用 `inject()` 重新处理，可以逐字节还原出原始 Steam 版脚本。

**调用点的两个 id 字段 ✅ 已定性**（920 处全量统计）：

| 字段 | 取值域 | 去重 | 含义 |
|---|---|---|---|
| 第一个 `0x0b` 的 u16（A） | 1089 … 1189 | 69 个 | CG 所属的**场景/图库分组** |
| 第二个 `0x0b` 的 u16（B） | 1190 … 2674 | 394 个 | **该 CG 的编号 = 索引 `CG_Achievement.ws2` 的键** |

⇒ 引擎侧的映射是「**CG 编号（B）→ `CG_Achievement.ws2` 条目 → CG 计数 `var[55]` → 收集里程碑 `F0 idx`**」；成就数据与触发条件完全由脚本层决定，**引擎只负责按 `F0` 的 idx 查运行时表并调用 Steam API**（表由 Steam 的 `GetAchievementName(i)` 顺序构建，见 [engine-mechanics.md](engine-mechanics.md)）。故**只要复用 Steam 版脚本里原样写好的 `0x0b` 变量对 + 那条 16 字节调用，就必然复现原版成就行为**，无需理解引擎内部实现。

## 定制 Lua 5.3 字节码（读 + 写）✅

`Script.arc` 里的 `.lua` 成员是 Lua 5.3 编译产物（签名 `\x1bLua` + `0x53`），不是混淆。读端在上游 `GalRev`（`galrev.advhd.luac53` / `luadis53`）；本项目在 `tool/lua53.py` 补上**序列化**（`dump`）。

与本作引擎相关的两个硬结论（首次改写字节码时实测）：

1. **字符串长度是 1 字节**（不是头部声明的 `sizeof(size_t)`）：长度字节 = `len+1`，载荷只有 `len` 字节（**不带 NUL**）。全部 14 个 `.lua` 成员 `dump(load(b)) == b` 逐字节往返通过。
2. **opcode 数值在本引擎相对上游 5.3 整体错位一位**：`luadis53` 在索引 9 处插了一个 `OP_UNKNOWN9`，因此 `SETTABLE` 起的所有助记符对应**本引擎 opcode = 上游 +1**（`RETURN=38` / `FORLOOP=39` / `FORPREP=40` / `SETLIST=43`；`LOADK=1` / `NEWTABLE=11` 不变）。**改字节码时 opcode 数值必须从本作样本实测反推，不能拿助记符表直接编号**（见 [lessons-learned.md](lessons-learned.md) 「反汇编器给出的助记符」…条）。

3. **跳转 sBx 的偏置是 `MAXARG_sBx = ((1<<18)-1)>>1 = 131071`，不是 131072**（`JMP`/`FORPREP`/`FORLOOP`/`TFORLOOP` 共用）。运算符优先级 `(1<<18)-1>>1` 是 `((1<<18)-1)>>1`，照抄「1<<17」当偏置会整体偏 1，而**读写都用同一个错偏置时往返看不出来**（写进去、读出来自洽），只有改成「插入一段指令并让新块自带 JMP」时才暴露。改字节码必须显式定义 `SBX_BIAS=131071` 并单独断言目标落位。

首次改写：`LegacyGame.lua` 的 `StoryMenuInit`（`proto [142,8]`）按钮表 7→8 —— `NEWTABLE` 表长 7→8、`SETLIST` 前插一条 `LOADK`、`SETLIST` 覆盖数 7→8、`FOR` 上界常量 7→8；新增常量**追加到常量池末尾**（既有下标不变）；插入指令会平移 pc，写盘器**重算全部 sBx**（`JMP`/`FORLOOP`/`FORPREP`/`TFORLOOP`）。写盘：`script/build/build_route_entry.py`。

## `.MOS` 马赛克变体 ✅ 身份已确认，选用机制待查

原版部分角色立绘目录（如 `CHIP3.arc` 的 HUT_10、CHIP6.arc 的 AMA_10）中，同名 `.png` 文件旁存在一个同名的 `.MOS` 文件（如 `HUT_10_006S.MOS` 与 `HUT_10_006S.png` 并存）。**已确认 `.MOS` 是马赛克遮罩变体**（本身也是合法 PNG，相同的 PNG magic bytes，但文件明显更小——12995 字节 vs 对应 png 的 1009838 字节）。

选用机制仍待查：已对原版 `Rio.arc` 全部 161 个脚本做过完整扫描（非抽样），确认没有任何脚本引用过 `.MOS` 扩展名。进一步核实：脚本中引用了与 `.MOS` 同名的图片 stem（如 `AMA_10_005B`）时，一律写作 `<stem>.PNG`，从未写作 `<stem>.MOS`（例如 `AMA_004.ws2` 中出现的是 `AMA_10_005B.PNG`）。说明脚本本身永远只请求 `.PNG`，`.MOS` 与 `.PNG` 之间的切换是引擎在加载资源时自行决定的，不受脚本控制。具体触发条件（游戏内审查开关？系统区域检测？）尚未查明，见下方待办。

另外已确认：Steam 版 `CHIP3.arc`、`CHIP6.arc` 中 `.MOS` 文件已被**整批移除**（数量为 0），Steam 版脚本中也不存在任何 `.MOS` 引用。也就是说 `.MOS` 变体属于 Steam 版删减范围的一部分，还原内容时如果涉及到原版中曾经存在 `.MOS`/`.png` 并存的立绘，需要考虑是否要一并带回 `.MOS` 变体（取决于是否需要还原引擎的马赛克切换行为，还是只需要保留清晰版 `.png` 即可）。
