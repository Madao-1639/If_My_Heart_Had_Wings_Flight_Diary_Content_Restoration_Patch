## 1. 路线入口机制 ✅（静态分析 `mainmenu.ws2`）

### 1.1 `mainmenu.ws2` = `var[98]` 分派表

`mainmenu.ws2`（Steam，1678 B，174 条指令）结构：

```
00014  01 Condition mode=3 id=127 value=0.0 → 0x41     ; flag[127] == 0 时继续，否则走回想
00024  06 Jump 907                                     ; flag[127] != 0 → 回想模式
00029  0b SetFlag 1049 1
0002d  1a OpenTitle  "openTitle"                       ; Lua：标题菜单
00038  01 Condition mode=130 id=99 value=100.0 → 0x745  ; var[99] == 100 → 剧情选择
00048  1c ExecuteFunction "openStory" 0 0              ; Lua：打开剧情选择界面
00057  01 Condition mode=130 id=98 value=0.0 → 0x6c     ; var[98] == 0 → 循环
00090  01 Condition mode=130 id=98 value=108.0 → 0xda   ; var[98] == 108 → 朱莉
000cf  07 NextFile "AKA_010_E"
000da  01 ... value=107.0 → 0x124   ; → AFT_001_E
00124  01 ... value=106.0 → 0x16e   ; → BEF_001_E
0016e  01 ... value=105.0 → 0x1b8   ; → HOT_001_E
001b8  01 ... value=104.0 → 0x203   ; → KAN_1001_E
00203  01 ... value=103.0 → 0x24d   ; → HUS_001_E
0024d  01 ... value=102.0 → 0x295   ; → AGS_001      ← 姬城あげは线（分支存在）
00295  01 ... value=101.0 → 0x2df   ; → NOV_001_E
```

- **`var[98]` = 路线按钮 id**；每个分支前置一段固定前导（`0e Unk0E 0 1000 0`、`0d 0 200 0.0`、`09 LayerConfig 0 10..13 1.0`）。
- **`var[99]` = 界面选择**（100 = 剧情选择，101–104 = 其他界面）。
- **`flag[127]` = 回想模式标记**（置位则整段跳过，走 `0x907` 的回想路径）。
- 与朱莉线**并列且同构** ⇒ 线路完备不需要改造分派表。

## 3. 「线路完备」的实现方案

1. **脚本**：把原版 `AGS_001.ws2` 按**本作编码**重新落地（⚠️ 原版与 Steam 是**不同引擎版本**，见 §5，不能直接照抄字节），注入 `CG_ACHIEVEMENT` 调用，落 `Rio.arc`。
2. **分派**：`mainmenu.ws2` **不用改**（`var[98]==102` 分支已在）。
3. **按钮表**：改 `LegacyGame.lua` 的 `StoryMenuInit`（proto `142/8`）—— `NEWTABLE` 表长 7→8、在 `SETLIST` 前插一条 `LOADK R12 := 102`、`SETLIST` 覆盖数 7→8（常量 102/8 追加到常量池末尾；插入的指令会平移 pc，写盘器**重算全部 sBx**）。新按钮几何沿用公式（i=8 → on=19、def=20）。
4. **滑入动画的上界**：`MenuEffectStart`（proto `142/4`）开界面时**逐个按钮**做滑入（从 `(目标−100,−100)` 缓动到目标位），它也是一个 `FOR i = 1, 7` 的硬编码上界 ⇒ **必须一起改成 8**，否则新按钮没有滑入动画（实机表现为“直接出现”）。这是“数据表改了一处、遍历硬编码在另一处”的典型缺口。取消动画的 `CancelMenuEffect`（`142/5`）走 `pairs(EffectButtonKeyList)`，无需改。
5. **图形**：`SYS_C_Story.pna` 的记录 **19（on/亮）、20（def/暗）** 由哨兵/空层变成第 8 对按钮图层。**不改记录数 ⇒ 子层编号不变**，所以 `StoryBace` 的其它子层索引（`31..39`、`41..43`）无需跟着改（详见 §3.5「不改层序」）。
6. **文案**：`姬城姐妹的日常`（日文原版 `アフターストーリー：姫城姉妹編` 的对仗译名；官中把平行的 `風戸姉妹編` 译作 `风户姐妹的日常`，`姬城萤的场合` 已把 ほたる 译作 萤）。
7. **朱莉线**：全程不动（`Rio1.arc` / `Chip10.arc` / `AKA_*` / `zh-CN/Rio1.arc`），由 `resource/julie_guard.json` 硬拒绝。

### 3.8 英/默认 UI 的入口（base PNA）

`getUItype() != 1`（英/默认）时用的是 **base `SysGraphic.arc` 的 `SYS_Story.pna`**，而 Lua 按钮表是两语言共用的 ⇒ base PNA 必须也补上记录 19/20，否则第 8 个按钮落在哨兵上、英文模式下不可见。

- **图形直接取原版日文**：原版 `SYS_Story.pna` 的记录 7/8 = 「アフターストーリー：姫城姉妹編」，**字节保真**落到 `resource/route_entry/base_entry_ags_{on,def}.png`，build 只从 `resource/` 读取（重建：`script/build/import_route_assets.py`）。本项目不做英文化，所以英文模式下入口文字与线路内容均为日文；后继者只需补英文化即可用。
- **位置**：base 的按钮与中文 PNA **在屏位置一致**（如 base `idx17 on box (111,0,230,191)` 恰是中文 `(85,-61,256,252)` 裁掉 `(26,61)` 的空白外框；实测两者第 7 按钮底板对齐偏移 `(0,-1)`、失配率 0.24%）。因此沿用原版图形自带的 box 约定：on `(-2,-60)`、def `(-15,-73)`（canvas 251 高；与中文的 -61/-74 在屏等价）。
- 写盘：`script/build/build_route_entry.py` → `asset/SysGraphic.arc`；验收：`script/checks/check_route_entry.py::check_base_pna`（记录 19/20 与原版对应记录**逐字节一致**、其余 43 层与 backup 相同）。

### 3.5 按钮图形怎么来（关键结论）

官中的 7 个按钮是**位图**（字体/字号/蓝色填充/白描边/45° 旋转/字距全部固化）。重新用字体排版无法复刻描边与亚像素位置 ⇒ 采用**逐字拼字**：

- 目标文案 `姬城姐妹的日常` 与官中既有按钮 `风户姐妹的日常` **等长（7 字）且同字体同字距** ⇒ 只需把左侧 2 字位（风/户）换成 姬/城。
- 姬/城 取自官中按钮 `姬城萤的场合`（同一字体）。其余 5 字（姐妹的日常）**逐像素保留**。
- 字距与字格原点差**运行时从像素实测**（蓝色连通域质心做公共斜率最小二乘 + 共有字「的」锚定），不硬编码；实测值 ≈ 字距 14.71 px、原点差 −0.91 px ⇒ 平移 −15.62 px（沿文字方向）。
- **位移动作用「整数像素拷贝」而非重采样**：1 个字位 ≈ `advance/√2` ≈ 11.05 px，取整到 11 后残余 0.05 px（远小于一像素）。双三次重采样会在硬边上振铃，且半径下的往返量化会让图像产生可见噪点 ⇒ 直接取证整平移。
- **掩膜用硬边、不羽化**：掩膜外**逐字节**保留官中按钮、掩膜内**逐字节**取来源整平移。⚠️ **不能羽化**——实测「姬」的描边左缘距掩膜左界只有 1.4 px，而 σ=1 的羽化核影响半径约 3 px ⇒ 羽化带会压在描边上，把白描边与底板交叉混起来、压暗 7–22 级，看起来就是「沿描边散布的小黑点」（见 [lessons-learned.md](lessons-learned.md) §34）。掩膜边界本身都落在底板上（「姬/城」的蓝色填充 t 区间与边界是分开的），硬边不会有接缝。
- **底板是半透明的**：官方按钮的底板是半透明白色蔼（alpha 沿栅格渐变，实测 78.8% 的底板像素满足 `RGB == alpha`），文字不透明 ⇒ 万一要软化掩膜，混合必须在**预乘空间**做（直接线性混两个直通 RGBA 会把 RGB 往 0 拉，在半透明处留下蓝/黑斑）。
- 产物已**定版入库**为 `resource/route_entry/ags_button_cn_{on,def}.png`（UI 已达预期，生成脚本随定版移除）；**build 只读入库件**，并用 `tool.agsbutton.verify` 对 `backup/` 的官方按钮复核五道闸。
- 验收工具 `tool/agsbutton.py`（`measure` + `verify`），回读校验五条：7 字位 + 箭头、未替换字位与官中目标同位、替换位等于来源平移后位置、**掩膜内逐字节 = 来源整数平移、掩膜外逐字节 = 目标**（防重采样/羽化回归）、**PNG 辅助块（gAMA/cHRM/bKGD/pHYs/tEXt）与官中目标一致**。
- **PNG 辅助块必须保留**：官中按钮带 `gAMA=45455`、`cHRM=sRGB`、`bKGD=(255,255,255)`、`pHYs`、`tEXt`；用 PIL 新存一个 PNG 会把这些全丢掉。`bKGD` 就是“不透明观众”合成时用的背景色（白）——丢了以后不同谱的查看器会把半透明底板往黑里合成，近透明像素看上去就是「黑点」。做法：保留模板的全部非 IDAT 块，只换 IDAT。

### 3.6 不改层序（为什么动记录 19/20 而不是插入 2 层）

- **子层编号 = PNA 记录下标**（含哨兵）：实证是 `MenuButtonSet` 的 `on/def/hit` 参数直接就是记录下标（逐字拼出按钮层落在 5..18、Return 落在 1/2），而记录 4/19/21 是哨兵也占号。
- 因此“插入 2 层”会把 22 之后的**全部子层号平移**，逼着把 Lua 里 `22..28 / 31..39 / 41..43` 等字面量全改一遍，还要同步改 base `SYS_Story.pna`（否则英/默认 UI 的背景层索引错位）。
- 改哨兵/空层为真实图层则**记录数不变、子层号不变**：只需动 Lua 的按钮表与 FOR 上界。代价是按钮组末尾的 `u0=2` 哨兵没了（按钮组变成“有始标记、无终标记”），而 PNA 里本就有无哨兵组（记录 `41..44` 与开头 `0..3`）⇒ 判定安全。

> ⚠️ 与国外补丁的差别：它把 AGS 线**硬接到 `HUS_001_E` 的尾跳**（`TITLE`→`AGS_001`）。**这是 hack，不是还原**——原版 `HUS_001` 的尾跳同样是 `EVRET`/`TITLE`（实测），本项目的做法是**恢复 UI 按钮**这条正路。

### 附-2：跨版本转换的**机制级**论证

> ⚠️ **方法论纪律**：本节只写**机制验证**过的结论。此前曾用「多出字段的取值分布」
> （6/7 恒为 0）来论证"填 0 安全"——**那是分布，不是机制，不能作为决策依据**。
> 分布只能用来**发现**候选值；定案必须靠机制。以下为重写后的论证链。

#### 2.1 机制事实一：指令长度由格式表决定（IDA 反汇编）

`sub_4D40B0`（格式表唯一使用者）逐类型码推进流指针，`sub_4D45E0` 返回每个类型码
消耗的字节数。详见附-3。

⇒ **Steam 表多出的那个类型码，引擎确实会多消费 1 字节（f32 则 4 字节）。**
⇒ 不补这个字节，流从该指令起整体错位。**跨版本转换是必需的**（机制，非分布）。

#### 2.2 机制事实二：转换是**纯结构性 padding**（逐指令校验）

`script/checks/convert_purity.py` 对全部原版脚本**每一条指令**验证：

| 判据 | 结果 |
|---|---|
| opcode 序列不变 | ✅ |
| 指令条数不变 | ✅ |
| 按该 opcode 的 CONV 规则剥掉新增字段后，操作数字节 == 原版操作数 | ✅ **199,983 / 199,983** |

带新增字段的 58,895 条分布：`0x11`×993、`0x14`×21,402、`0x15`×21,347、
`0x16`×3,794、`0x1c`×876、`0x1e`×491、`0x28`×9,992。

⇒ **转换不改变、不重排、不丢失任何原有操作数**，唯一动作是插入一个新字段。
⇒ 转换的**语义风险面被压缩到唯一一个自由度：新字段填什么值**。

#### 2.3 机制事实三：新字段的取值 = 参考实现的取值

- Steam 工具链自己产出的脚本（即本游戏实际运行的脚本）在该字段上**一律**为 0 / 0.0
  （Steam 语料 111 剧本、约 6.6 万处，无一例外）。
- 本项目转换后填入的也是 0 / 0.0。

⇒ **产物与参考实现在「解释器会读到的每一个字节」上同构**：opcode 序列相同、
原有操作数逐字节相同、新增字段取值相同。引擎既然能正确执行它自己的脚本，
就能以同一机制执行我们的脚本。

> 这不是"分布推断"，而是**参考实现等价**：我们不猜测什么值"可能对"，
> 而是**复刻参考实现的取值**。

#### 2.4 已定位但尚未机制验证的部分（如实记录）

| 项 | 状态 |
|---|---|
| 解释器按格式表消费字节 | ✅ IDA 反汇编（附-3） |
| 转换纯 padding、原操作数逐字节不变 | ✅ `script/checks/convert_purity.py`（199,983 条，0 异常） |
| 新字段取值与参考实现一致 | ✅ 逐字节比对（产物 vs Steam 脚本） |
| `0x14` 的 handler 不读末位操作数 | ✅ IDA：`sub_402EB0` `case 20` 只取 `operand[2]` |
| `0x11`/`0x15`/`0x16`/`0x1c`/`0x1e`/`0x28` 的 handler 是否读末位操作数 | ⬜ **未验证**（已定位 VM 主循环 `sub_486B80` 与文本路径 `sub_402EB0`，但未逐个 handler 追到） |

**为什么第 5 项不影响结论**：由 2.2，转换不改变任何原有操作数；由 2.3，
新增字段的取值与参考实现相同。因此**即使**某个 handler 会读该字段，
读到的也是"Steam 官方脚本在该位置读到的同一个值"——行为与官方脚本一致。

### 附-3：解释器主循环的**反汇编级**验证（IDA）

格式表是否真的驱动指令步进？已在 Steam `AdvHD.exe`（IDB `AdvHD.exe.unpacked.exe.i64`，
image 0x1bd000）里找到答案。

**唯一引用格式表 `off_57ADA8` 的函数是 `sub_4D40B0`**（397 B，28 个基本块）。
其反编译核心：

```c
v9 = (char *)*(&off_57ADA8 + a4);          // a4 = opcode ⇒ 取该 opcode 的格式串
if ( v9 != nullptr ) {
    if ( *v9 < 0 ) { *a2 = v7; }           // 首字节 >= 0x80 ⇒ 空操作数
    else while ( 1 ) {
        v10 = v9[v8];                       // 逐个取类型码
        if ( v10 == 7 ) break;              // 类型 7 = 计数标记
        v12 = (const CHAR *)(*a3 + v5[5]);  // v12 = 流内当前位置
        if ( (unsigned)v10 > 0xA ) v13 = 0; // 类型 > 10 ⇒ 0 字节
        else v13 = sub_4D45E0(v10, ..., v12, ...);   // 读一个操作数
        *a3 = v13 + v11;                    // ★ 流指针按「读到的字节数」前进
        ++v8;
        if ( v28[v8] < 0 ) goto LABEL_10;   // 下一个类型码 >= 0x80 ⇒ 本指令结束
    }
    // 类型 7 分支：先读计数字节，再把下一个类型码重复 count 次
}
```

**`sub_4D45E0`（类型码 → 字节数读取器）** 是 `switch (a7)` 共 11 个 case，
每个 case 读一个 `VARIANTARG` 并返回 `a6 + 尺寸`：

| case（类型码） | 读取 | VARIANT vt | 返回 |
|---|---|---|---|
| 0 | `*a4`（BYTE） | 17 (VT_UI1) | `a6 + 1` |
| 1 | `*(_WORD*)a4` | 2 (VT_I2) | `a6 + 2` |
| 2 | `*(_WORD*)a4` | 18 (VT_UI2) | `a6 + 2` |
| 3 / 4 / 5 | `*(LONG*)a4` | VT_I4 / VT_UI4 / VT_R4 | `a6 + 4` |
| 6 / 9 / 10 | `SysAllocString`（NUL 终止串） | VT_BSTR | 串长 + 1 |

⇒ **结论（机器码级）**：指令长度**完全由格式表的类型码串决定**，流指针按每个类型码实际
消耗的字节数前进。因此 **Steam 表里多出的那个类型码 = 引擎确实会多消费 1 字节（或 4 字节）**
——不补这个字节，流从该指令起整体错位，这正是实测到的现象。本项目的 `ws2conv` 按两表
差分补默认值（0 / 0.0）与 Steam 编译器的产出**逐字节同构**。

这也解释了用户提出的机理假设：**Steam 构建把这些 opcode 的 handler 签名改了（多一个参数），
脚本编译器按各自 API 填默认值**——在机器码层面就体现在「格式串多了个类型码」。
